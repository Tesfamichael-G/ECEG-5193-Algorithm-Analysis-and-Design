    ECEG-4191¶

    Chapter 4 — Logical Design and Normalisation¶

    Learning outcomes¶

    1. Apply the **7-step ER-to-relational mapping** to any ER diagram.
    2. Apply the **2 extra steps** for EER constructs (specialisation, categories).
    3. Compute **closures** and **minimal covers** for sets of functional dependencies.
    4. Determine whether a schema is in **1NF, 2NF, 3NF, BCNF**.
    5. Decompose a schema into 3NF or BCNF while preserving properties.

    4.1 — ER-to-Relational Mapping Overview¶

    The 7 steps (Elmasri §9.1)
    Step Maps
    1 Regular entity types
    2 Weak entity types
    3 Binary 1:1 relationships
    4 Binary 1:N relationships
    5 Binary M:N relationships
    6 Multivalued attributes
    7 N-ary relationships
    !!! tip "The order matters" Steps 1–2 handle entities and their attributes. Steps 3–5 handle relationships. Steps 6–7 handle the "extras". Following the order avoids duplicate table creation.

    4.2 — Step 1: Regular Entity Types¶

    Rule

    Each regular entity becomes a relation: - Include all simple attributes. - For each composite attribute, include only its simple components. - Choose one key attribute as the primary key.

    ???+ info "Example: `EMPLOYEE(ssn, name(first, middle, last), sex, address, salary, bdate)`" Becomes: 
    CREATE TABLE EMPLOYEE (
    ssn     CHAR(9) PRIMARY KEY,
    first_name VARCHAR(30),
    middle_name VARCHAR(30),
    last_name   VARCHAR(30),
    sex     CHAR(1),
    address VARCHAR(100),
    salary  DECIMAL(10,2),
    bdate   DATE
);
    !!! warning "Don't create a table for the composite attribute" `name` is composite, but it is **not** a separate table. Its **simple components** (`first_name`, `middle_name`, `last_name`) become columns of `EMPLOYEE`.

    4.3 — Step 2: Weak Entity Types¶

    Rule

    Each weak entity becomes a relation with: - Its own attributes. - The owner's primary key as a foreign key. - Primary key = (owner's primary key, partial key).

    ???+ info "Example: `DEPENDENT`" 
    CREATE TABLE DEPENDENT (
    essn            CHAR(9),
    dependent_name  VARCHAR(50),
    sex             CHAR(1),
    birth_date      DATE,
    relationship    VARCHAR(20),
    PRIMARY KEY (essn, dependent_name),
    FOREIGN KEY (essn) REFERENCES EMPLOYEE(ssn)
);
    !!! tip "The full key is composite" `dependent_name` is a **partial key** — unique only within one employee. The full key must include `essn` to be globally unique.

    4.4 — Step 3: Binary 1:1 Relationships¶

    Rule

    Put the primary key of one side as a foreign key in the other side.

    Prefer the side with total participation — that ensures every tuple on that side has a non-NULL reference.

    ???+ info "Example: `EMPLOYEE MANAGES DEPARTMENT` (1:1)" Both sides are partial in the COMPANY model. Standard choice: put the foreign key in `DEPARTMENT`: 
    ALTER TABLE DEPARTMENT
    ADD COLUMN mgr_ssn CHAR(9),
    ADD FOREIGN KEY (mgr_ssn) REFERENCES EMPLOYEE(ssn);
    !!! warning "Why NOT in EMPLOYEE?" If `mgr_dno` were in `EMPLOYEE`, most employees would have NULL there (only one manager per department). Putting the reference in `DEPARTMENT` is more natural.
    ???+ note "The cross-reference option" An alternative is a **cross-reference table** with both foreign keys. This is used when neither side has total participation and the relationship has its own attributes.

    4.5 — Step 4: Binary 1:N Relationships¶

    Rule

    Put the primary key of the "1" side as a foreign key in the "N" side.

    This is the most common mapping — every EMPLOYEE has one dno.

    ???+ info "Example: `EMPLOYEE WORKS_FOR DEPARTMENT` (N:1)" 
    ALTER TABLE EMPLOYEE
    ADD COLUMN dno INT,
    ADD FOREIGN KEY (dno) REFERENCES DEPARTMENT(dnumber);
    !!! tip "Total participation ⇒ NOT NULL" Because every employee must work for a department (total participation), add `NOT NULL`: 
    ALTER TABLE EMPLOYEE ADD COLUMN dno INT NOT NULL;

    4.6 — Step 5: Binary M:N Relationships¶

    Rule

    Create a new relation with: - The primary keys of both sides as foreign keys. - Any relationship attributes (e.g., hours). - Primary key = the combination of both foreign keys.

    ???+ info "Example: `EMPLOYEE WORKS_ON PROJECT` (M:N with `hours`)" 
    CREATE TABLE WORKS_ON (
    essn  CHAR(9),
    pno   INT,
    hours DECIMAL(3,1),
    PRIMARY KEY (essn, pno),
    FOREIGN KEY (essn) REFERENCES EMPLOYEE(ssn),
    FOREIGN KEY (pno)  REFERENCES PROJECT(pnumber)
);
    !!! warning "M:N cannot be a foreign key on either side" A single `EMPLOYEE.ssn` cannot reference many projects, and a single `PROJECT.pnumber` cannot reference many employees. The cross-reference table is **required**.

    4.7 — Step 6: Multivalued Attributes¶

    Rule

    Create a new relation with: - The multivalued attribute itself. - The owner's primary key as a foreign key. - Primary key = (owner's primary key, attribute).

    ???+ info "Example: `DEPARTMENT.locations` (multivalued)" 
    CREATE TABLE DEPT_LOCATIONS (
    dnumber   INT,
    dlocation VARCHAR(50),
    PRIMARY KEY (dnumber, dlocation),
    FOREIGN KEY (dnumber) REFERENCES DEPARTMENT(dnumber)
);
    !!! tip "Why not keep it in DEPARTMENT?" A relational attribute must be **atomic** (1NF). A multivalued attribute would violate 1NF. The separate table is the standard fix.

    4.8 — Step 7: N-ary Relationships¶

    Rule

    Create a new relation with: - The primary keys of all participating entities as foreign keys. - Any relationship attributes. - Primary key = the combination of all foreign keys (or a subset if some participants are functionally determined).

    ???+ info "Example: `SUPPLIES(supplier, project, part, quantity)`" 
    CREATE TABLE SUPPLIES (
    supplier_id INT,
    project_id  INT,
    part_id     INT,
    quantity    INT,
    PRIMARY KEY (supplier_id, project_id, part_id),
    FOREIGN KEY (supplier_id) REFERENCES SUPPLIER(supplier_id),
    FOREIGN KEY (project_id)  REFERENCES PROJECT(project_id),
    FOREIGN KEY (part_id)     REFERENCES PART(part_id)
);
    !!! warning "Ternary ≠ three binary relationships" A ternary `SUPPLIES` means "supplier supplies part **to** project" — a joint constraint. Three separate binary relationships would lose the joint semantics.

    Worked example 4.1 — Map the COMPANY database¶

    Problem:

    Map the COMPANY ER model from Chapter 3 to a relational schema.

    ???+ note "**Step 1 — regular entities.**" 
    CREATE TABLE EMPLOYEE (
    ssn CHAR(9) PRIMARY KEY,
    first_name VARCHAR(30), middle_name VARCHAR(30), last_name VARCHAR(30),
    sex CHAR(1), address VARCHAR(100), salary DECIMAL(10,2), bdate DATE
);
CREATE TABLE DEPARTMENT (
    dnumber INT PRIMARY KEY,
    dname VARCHAR(50) UNIQUE
);
CREATE TABLE PROJECT (
    pnumber INT PRIMARY KEY,
    pname VARCHAR(50), location VARCHAR(50)
);
    ??? info "**Step 2 — weak entity.**" 
    CREATE TABLE DEPENDENT (
    essn CHAR(9),
    dependent_name VARCHAR(50),
    sex CHAR(1), birth_date DATE, relationship VARCHAR(20),
    PRIMARY KEY (essn, dependent_name),
    FOREIGN KEY (essn) REFERENCES EMPLOYEE(ssn)
);
    ??? info "**Step 3 — 1:1 `MANAGES`.**" 
    ALTER TABLE DEPARTMENT ADD COLUMN mgr_ssn CHAR(9),
    ADD FOREIGN KEY (mgr_ssn) REFERENCES EMPLOYEE(ssn);
    ??? info "**Step 4 — 1:N `WORKS_FOR`, `CONTROLS`, `SUPERVISES`.**" 
    ALTER TABLE EMPLOYEE ADD COLUMN dno INT,
    ADD FOREIGN KEY (dno) REFERENCES DEPARTMENT(dnumber);
ALTER TABLE EMPLOYEE ADD COLUMN super_ssn CHAR(9),
    ADD FOREIGN KEY (super_ssn) REFERENCES EMPLOYEE(ssn);
ALTER TABLE PROJECT ADD COLUMN dnum INT,
    ADD FOREIGN KEY (dnum) REFERENCES DEPARTMENT(dnumber);
    ??? info "**Step 5 — M:N `WORKS_ON`.**" 
    CREATE TABLE WORKS_ON (
    essn CHAR(9), pno INT, hours DECIMAL(3,1),
    PRIMARY KEY (essn, pno),
    FOREIGN KEY (essn) REFERENCES EMPLOYEE(ssn),
    FOREIGN KEY (pno)  REFERENCES PROJECT(pnumber)
);
    ??? info "**Step 6 — multivalued `locations`.**" 
    CREATE TABLE DEPT_LOCATIONS (
    dnumber INT, dlocation VARCHAR(50),
    PRIMARY KEY (dnumber, dlocation),
    FOREIGN KEY (dnumber) REFERENCES DEPARTMENT(dnumber)
);
    ??? success "**Result.**" Seven tables: `EMPLOYEE`, `DEPARTMENT`, `PROJECT`, `DEPENDENT`, `WORKS_ON`, `DEPT_LOCATIONS`. All keys and foreign keys defined. No redundancy.

    4.9 — EER Extra Steps¶

    Step 8 — Specialisation / Generalisation

    Four options (Elmasri §9.2):

    Option Structure When to use
    8A Superclass table + subclass tables (each references superclass) Any specialisation
    8B Subclass tables only (each contains all superclass attributes) Total, disjoint specialisation
    8C Single table + type discriminator Disjoint, no subclass-specific attributes
    8D Single table + multiple boolean type attributes Overlapping
    ???+ note "Step 9 — Categories (Union types)" Create one relation per subclass, plus a **category table** that holds the primary key of each participant and a **type discriminator**. The category table's rows reference the appropriate subclass tables.

    Worked example 4.2 — Map EER specialisation (8A vs 8C)¶

    Problem:

    EMPLOYEE has subclasses SECRETARY(typing_speed) and ENGINEER(engineering_field). Specialisation is disjoint, total. Map it two ways.

    ???+ note "**Option 8A — separate tables.**" 
    CREATE TABLE EMPLOYEE (
    ssn CHAR(9) PRIMARY KEY, first_name VARCHAR(30), last_name VARCHAR(30),
    salary DECIMAL(10,2), dno INT
);
CREATE TABLE SECRETARY (
    ssn CHAR(9) PRIMARY KEY,
    typing_speed INT,
    FOREIGN KEY (ssn) REFERENCES EMPLOYEE(ssn)
);
CREATE TABLE ENGINEER (
    ssn CHAR(9) PRIMARY KEY,
    engineering_field VARCHAR(50),
    FOREIGN KEY (ssn) REFERENCES EMPLOYEE(ssn)
);
    Every employee query must `JOIN` with the subclass table.
    ??? info "**Option 8C — single table with discriminator.**" 
    CREATE TABLE EMPLOYEE (
    ssn CHAR(9) PRIMARY KEY, first_name VARCHAR(30), last_name VARCHAR(30),
    salary DECIMAL(10,2), dno INT,
    emp_type CHAR(1) CHECK (emp_type IN ('S','E')),
    typing_speed INT,
    engineering_field VARCHAR(50)
);
    Subclass-specific attributes are NULL for the "wrong" type. **Simpler** queries but **NULLs** everywhere.
    ??? success "**Which to choose?**" - **8A** when there are **many** subclass-specific attributes and queries usually touch subclasses separately. - **8C** when subclass-specific attributes are **few** and queries usually join back to the superclass.

    4.10 — Functional Dependencies (FDs)¶

    Definition (Elmasri §14.2)

    A functional dependency \(X \to Y\) on relation \(R\) holds if, for every two tuples \(t_1, t_2\) of \(R\):

    \[ t_1[X] = t_2[X] \implies t_1[Y] = t_2[Y]. \]

    In words: \(X\) determines \(Y\) — the value of \(X\) uniquely determines the value of \(Y\).

    ???+ info "Example" - `ssn → name` — two employees with the same SSN have the same name. - `ssn → (name, bdate, address)` — an SSN determines the whole employee record. - `(ssn, pno) → hours` — the hours on a project depend on both the employee and the project.
    !!! warning "The direction is one-way" `X → Y` **does not** imply `Y → X`. `ssn → name` holds, but `name → ssn` does not (two employees can share a name).

    4.11 — Armstrong's Axioms¶

    Three inference rules (sound and complete)

    Reflexivity. If \(Y \subseteq X\), then \(X \to Y\).

    Augmentation. If \(X \to Y\), then \(XZ \to YZ\) for any \(Z\).

    Transitivity. If \(X \to Y\) and \(Y \to Z\), then \(X \to Z\).

    ???+ info "Derived rules" - **Union:** $X \to Y$ and $X \to Z$ ⇒ $X \to YZ$. - **Decomposition:** $X \to YZ$ ⇒ $X \to Y$ and $X \to Z$. - **Pseudotransitivity:** $X \to Y$ and $WY \to Z$ ⇒ $WX \to Z$.
    !!! tip "Sound and complete" **Sound** = every derived FD is true in every instance satisfying the original FDs. **Complete** = every FD implied by the originals can be derived. Armstrong's axioms are both.

    4.12 — Closure of Attribute Sets¶

    Definition

    The closure \(X^+\) of an attribute set \(X\) under \(F\) is the set of all attributes functionally determined by \(X\) using Armstrong's axioms.

    ???+ info "Algorithm" 
    X+ := X
repeat:
    for each FD (A → B) in F:
        if A ⊆ X+ and B ⊄ X+:
            X+ := X+ ∪ B
until X+ does not change
    ???+ success "Uses of closure" - **Test if $X$ is a superkey:** $X^+$ = all attributes. - **Test if $X \to Y$ holds:** $Y \subseteq X^+$. - **Compute candidate keys:** find minimal $X$ with $X^+$ = all attributes.

    Worked example 4.3 — Compute \((AB)^+\)¶

    Problem:

    \(R(A,B,C,D,E)\) with \(F = \{AB \to C,\ C \to D,\ D \to E\}\). Compute \((AB)^+\).

    ???+ note "**Step 1 — initialise.**" $(AB)^+ = \{A, B\}$.
    ??? info "**Step 2 — apply FDs.**" - $AB \to C$: $AB \subseteq (AB)^+$, so add $C$ → $\{A,B,C\}$. - $C \to D$: $C \subseteq (AB)^+$, so add $D$ → $\{A,B,C,D\}$. - $D \to E$: $D \subseteq (AB)^+$, so add $E$ → $\{A,B,C,D,E\}$.
    ??? success "**Result.**" $(AB)^+ = \{A, B, C, D, E\}$ — all attributes. So $AB$ is a **superkey**. **Is $AB$ a candidate key?** Check $(A)^+ = \{A\}$, $(B)^+ = \{B\}$ — neither. So $AB$ is a **candidate key** (minimal).

    4.13 — Minimal Cover¶

    Definition

    A minimal cover \(F_{\min}\) of \(F\) is a set of FDs equivalent to \(F\) such that:

    1. Every FD has a single attribute on the right.
    2. No redundant FD — removing any loses equivalence.
    3. No redundant attribute on the left — the left side is minimal.
    ???+ info "Algorithm" 1. Decompose RHS: $X \to AB$ becomes $X \to A$, $X \to B$. 2. Remove redundant LHS attributes: if $A$ is redundant in $AB \to C$ (i.e., $B \to C$ after removing $A$), drop $A$. 3. Remove redundant FDs: for each FD, remove it and see if it's still implied.
    !!! tip "Minimal covers are not unique" Different removal orders give different but equivalent minimal covers. Any is valid.

    Worked example 4.4 — Compute a minimal cover¶

    Problem:

    \(F = \{A \to B, ABCD \to E, EF \to G, EF \to H, ACDF \to EG\}\). Compute a minimal cover.

    ???+ note "**Step 1 — decompose RHS.**" - $A \to B$ - $ABCD \to E$ - $EF \to G$, $EF \to H$ - $ACDF \to E$, $ACDF \to G$
    ??? info "**Step 2 — remove redundant LHS attributes.**" - For $ABCD \to E$: is $B, C, D$ redundant? Compute $(ACD)^+$. $A \to B$, so $(ACD)^+ \supseteq ABCD \to E$. So $B$ is redundant. New FD: $ACD \to E$. - Similarly, $C$ and $D$ may be reducible further; compute $(AD)^+ \supseteq E$? Check step by step.
    ??? info "**Step 3 — remove redundant FDs.**" Test each FD by removing it and checking if the remainder implies it via closure.
    ??? success "**Result.**" A possible minimal cover: $\{A \to B, A \to E, A \to G, EF \to H\}$ (depending on redundancy analysis). The exact form varies, but the closure is preserved.

    4.14 — Normal Forms Overview¶

    The four normal forms
    Normal Form Removes Requires
    1NF Multivalued attributes Atomic values
    2NF Partial dependencies 1NF + no partial dependency on part of a key
    3NF Transitive dependencies 2NF + every FD has superkey LHS or prime RHS
    BCNF All non-superkey determinants 3NF + every FD has superkey LHS
    !!! tip "The hierarchy" BCNF $\subset$ 3NF $\subset$ 2NF $\subset$ 1NF. Every BCNF relation is 3NF, every 3NF is 2NF, every 2NF is 1NF.

    4.15 — 1NF — First Normal Form¶

    1NF (Elmasri §14.3)

    A relation is in 1NF if every attribute value is atomic — no sets, no lists, no nested relations.

    ???+ info "Violation example" 
    STUDENT(student_id, name, phones)
101, Alice, {555-1234, 555-5678}      ← multivalued
    Fix: separate table `STUDENT_PHONE(student_id, phone)`.
    !!! warning "1NF is not optional" Relational algebra and SQL assume atomic values. Without 1NF, projection, join, and aggregate become ill-defined.

    4.16 — 2NF — Second Normal Form¶

    2NF

    A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on every candidate key.

    ???+ info "What is a partial dependency?" A **partial dependency** exists when a non-prime attribute depends on **part** of a composite candidate key, not the whole key. Example: `WORKS_ON(essn, pno, hours, ename)` with FD `essn → ename`. `ename` depends only on `essn`, part of the composite key `(essn, pno)`. **Violates 2NF.**
    ???+ info "Fix" Decompose so that every non-prime attribute depends on the full key: 
    EMPLOYEE(ssn, ename, ...)
WORKS_ON(essn, pno, hours)
    !!! tip "2NF only matters for composite keys" If a relation has a single-attribute primary key, it is **automatically in 2NF** — no partial dependency is possible.

    4.17 — 3NF — Third Normal Form¶

    3NF (Elmasri §14.4)

    A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on any candidate key.

    Equivalently: for every non-trivial FD \(X \to Y\):

    • \(X\) is a superkey, or
    • \(Y\) is a prime attribute (part of some candidate key).
    ???+ info "What is a transitive dependency?" `X → Y → Z` where `X` is a key and `Z` is non-prime. `Z` depends on `X` only through `Y`. Example: `EMPLOYEE(ssn, name, dno, dname)`. `ssn → dno` (key → non-key) and `dno → dname` (non-key → non-key). `dname` is transitively dependent on `ssn`. **Violates 3NF.**
    ???+ info "Fix" Decompose into `EMPLOYEE(ssn, name, dno)` and `DEPARTMENT(dno, dname)`.

    4.18 — BCNF — Boyce-Codd Normal Form¶

    BCNF

    A relation is in BCNF if, for every non-trivial FD \(X \to Y\):

    \(X\) is a superkey.

    (No exception for prime attributes.)

    ???+ info "BCNF is stricter than 3NF" 3NF allows $Y$ prime even when $X$ is not superkey. BCNF forbids this. Example: `R(A,B,C)` with `AB → C, C → B`. Candidate keys: `AB`, `AC`. `C → B` has non-superkey `C` but prime `B` → **3NF but not BCNF**.
    !!! warning "BCNF may lose dependency preservation" The classic 3NF-but-not-BCNF relation above cannot be BCNF-decomposed without losing the FD `AB → C`. So 3NF is the practical target when dependency preservation matters.

    Worked example 4.5 — Full normalisation¶

    Problem:

    EMP_PROJ(ssn, ename, pno, pname, hours)
    FDs: ssn → ename, pno → pname, (ssn, pno) → hours. Normalise to 3NF.

    ???+ note "**Step 1 — candidate key.**" Only `(ssn, pno)` is a candidate key. Prime attributes: `ssn`, `pno`. Non-prime: `ename`, `pname`, `hours`.
    ??? info "**Step 2 — check 1NF.**" All values atomic. **Satisfied.**
    ??? info "**Step 3 — check 2NF.**" `ssn → ename`: partial dependency (ename on ssn only). `pno → pname`: partial dependency. **Violates 2NF.**
    ??? info "**Step 4 — decompose for 2NF.**" - `EMP(ssn, ename)` - `PROJ(pno, pname)` - `WORKS_ON(ssn, pno, hours)`
    ??? info "**Step 5 — check 3NF.**" - `EMP`: `ssn` is the key; `ssn → ename` OK. - `PROJ`: `pno` is the key; `pno → pname` OK. - `WORKS_ON`: `(ssn, pno)` is the key; `(ssn, pno) → hours` OK. No transitive dependencies. **All three are in 3NF (and in BCNF).**
    ??? success "**Result.**" `EMP(ssn, ename)`, `PROJ(pno, pname)`, `WORKS_ON(ssn, pno, hours)` — lossless, dependency-preserving, in BCNF.

    Worked example 4.6 — 3NF but not BCNF¶

    Problem:

    R(A, B, C) with FDs AB → C, C → B. Is it in 3NF? BCNF?

    ???+ note "**Step 1 — candidate keys.**" - $(AB)^+ = \{A, B, C\}$ → `AB` is a candidate key. - $(AC)^+ = \{A, C, B\}$ → `AC` is a candidate key. Prime attributes: `A, B, C`. Non-prime: none.
    ??? info "**Step 2 — check 3NF.**" For every FD $X \to Y$: $X$ superkey **or** $Y$ prime. - `AB → C`: `AB` is superkey. ✓ - `C → B`: `C` not superkey, but `B` is prime → satisfies 3NF. ✓
    ??? info "**Step 3 — check BCNF.**" `C → B`: `C` is not a superkey. **Violates BCNF.**
    ??? success "**Conclusion.**" The relation is **3NF but not BCNF**.
    ???+ warning "BCNF decomposition loses dependency" Decompose into `R1(C, B)` and `R2(A, C)`. Lossless, BCNF. But `AB → C` now requires a **join** to verify — **dependency not preserved**.

    4.19 — Decomposition Properties¶

    Two desirable properties
    Property Meaning
    Lossless join The natural join of the decomposed relations reconstructs the original exactly (no spurious tuples)
    Dependency preservation Every FD of the original is enforceable within a single decomposed relation
    ???+ info "Testing for lossless join (binary decomposition)" For $R$ decomposed into $R_1$ and $R_2$: **Lossless iff** $R_1 \cap R_2 \to R_1$ **or** $R_1 \cap R_2 \to R_2$ holds.
    ???+ info "The 3NF synthesis algorithm" 1. Compute a minimal cover $F_{\min}$. 2. For each FD $X \to A$ in $F_{\min}$, create a relation $XA$. 3. If no relation contains a candidate key of $R$, add one. **Guarantees:** lossless, dependency-preserving, 3NF.
    ???+ warning "BCNF decomposition is lossless but not dependency-preserving" The classic 3NF-not-BCNF example shows that BCNF and dependency preservation can conflict. **3NF is the practical target** for OLTP systems.

    4.20 — Informal Design Guidelines¶

    Three guidelines (Elmasri §14.1)

    1. Clear semantics. Each tuple should represent one entity or relationship, and each attribute should describe one property of that entity.

    ???+ note "2. No redundant information" Redundancy causes **update, insertion, and deletion anomalies**. The goal of normalization is to eliminate structural redundancy.
    ???+ note "3. Few NULLs" Excessive NULLs waste space and complicate joins, aggregates, and constraints. NULLs also indicate **ambiguous design**.
    !!! tip "Normalization is a design guideline, not a law" Sometimes denormalization is **deliberate** — data warehouses denormalize for query performance. But OLTP systems should normalize to 3NF (or BCNF when possible).

    Chapter 4 — key takeaways¶

    **1.** The **7-step ER-to-relational mapping** transforms any ER diagram into a relational schema. Order matters.
    **2.** **EER specialisations** have four mapping options (8A–8D); **categories** use a type-discriminator table.
    **3.** **Functional dependencies** $X \to Y$ mean $X$ determines $Y$. **Armstrong's axioms** (reflexivity, augmentation, transitivity) are sound and complete.
    **4.** **Closure** $X^+$ tests whether $X$ is a superkey and whether $X \to Y$ holds. **Minimal cover** reduces FDs to their essential form.
    **5.** **1NF** = atomic values. **2NF** = no partial dependency. **3NF** = no transitive dependency. **BCNF** = every determinant is a superkey.
    **6.** **Lossless join** and **dependency preservation** are the two goals of decomposition. **3NF synthesis** achieves both; **BCNF decomposition** achieves only losslessness.
